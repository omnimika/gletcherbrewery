# ADR 0005 — Rich-content CMS (blog editor)

> Status: **Proposed** (owner preference Confirmed for editor; install deferred)  
> Stage: Public blog migration (sprint 3+) → CRM later  
> Does **not** choose ORM, auth, or database (see reserved `0002`/`0003`/`0004`).

## Context

Tilda feed posts store body as an ordered JSON array of redactor blocks
(`preface`, `text`, `heading`+`le`, `image`, …). Sprint 2 listing uses fixtures;
sprint 3 needs a public article renderer. Owner will edit/create blog posts in
the future CRM with **[Puck](https://puckeditor.com/docs)** (MIT, React, no
vendor lock-in on data). Block types should mirror the Tilda blog editor so
migration and editorial habits stay aligned.

NocoDB remains tabular admin — **not** a rich-content CMS.

## Decision (Proposed)

1. **Canonical body model** = typed block list (not trusted raw Tilda HTML).
   Public Next.js renders the same block types the CRM will edit.
2. **CRM editor (future):** Puck, configured with components that match the
   block taxonomy below. Data owned by the app (PostgreSQL / Object Storage) —
   Puck is UI, not the source of truth.
3. **Do not install Puck, CMS packages, or DB** until the CRM stage is approved.
   Sprint 3–4 use JSON/TS fixtures + the public block renderer only.
4. **Tilda → blocks** import maps feed `ty` values into this taxonomy; strip
   scripts/runtime; sanitize inline marks (`strong` / `em` / `a` / `br` only).

### Block taxonomy (Tilda feed ↔ Puck component)

| Tilda `ty` / DOM | App / Puck type | Sprint 3 |
|---|---|---|
| `preface` (`blockquote.t-redactor__preface`) | `preface` | Yes (pizza) |
| `text` (`div.t-redactor__text`) | `paragraph` | Yes |
| `heading` + `le` (`h3.t-redactor__h3`, …) | `heading` (`level` 2–4) | Yes |
| `image` (`figure` + url/alt/caption) | `image` | Yes |
| quote (when present) | `quote` | Reserved |
| list / ul / ol | `list` | Reserved |
| video / embed | `video` | Open |
| free HTML | — | **Rejected** as trusted input |

Cover/title/date/category stay **post metadata**, not body blocks (same as Tilda
feed fields `title` / `image` / `date` / parts).

### Puck integration sketch (future CRM)

- One Puck `Config` component per app block type; `data.content` ≈ `BlogBlock[]`
  (or thin adapter). See Puck [component configuration](https://puckeditor.com/docs/integrating-puck/component-configuration)
  and [data model](https://puckeditor.com/docs/api-reference/data-model).
- Locales: separate translation documents (ADR 0001), not one Puck tree with
  mixed languages.
- Media: upload to Object Storage; store public URL + alt on `image` blocks.

## Consequences

- Article template and batch import share one renderer → CRM later reuses it.
- Inventing a different WYSIWYG HTML blob would fight Puck and Tilda parity.
- Reserved block types may appear in import reports as `unsupported` until
  mapped — do not silently drop without a manifest note.

## Open
